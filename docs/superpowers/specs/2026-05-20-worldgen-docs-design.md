# How Oxium Builds a World — Documentation Site Design

**Date:** 2026-05-20
**Status:** Approved, ready for implementation planning
**Branch:** TBD (implementation will happen in a separate git worktree)

## Summary

Design and publish a deep, pedagogical documentation corpus for the Oxium engine — built as a **Docusaurus** site at `docs/book/` in the repo, deployed to GitHub Pages. The book teaches a reader with a CS degree (but no graphics/math-specific background) how the engine works, from first principles up through every layer of the worldgen pipeline and, eventually, the rendering / engineering substrate. The book is written in a Rust-Book-flavored voice (second person, code-first, generous worked examples) with inline interactive React widgets at the points where dragging-a-slider beats looking-at-a-static-image.

**Working title:** *How Oxium Builds a World*.

**Audience contract** (printed in the preface): the reader has a CS degree but no graphics/games-math background; the book never says "obviously" about anything outside CS101 + linear algebra. It assumes comfort with Rust syntax and ownership at a "can read but not fluent" level.

The corpus ships in three phases. Only Phase 1 (Foundations + Worldgen) is scoped in detail here; Phases 2 and 3 are outlined so the site structure can accommodate them without rework.

| Phase | Scope | Milestone |
|---|---|---|
| **Phase 1** | Foundations + Worldgen (Parts I–V, ~30 chapters) | v1.0 of the book — standalone, publishable |
| **Phase 2** | Rendering, Meshing, Lighting (Parts VI–VIII) | v2.0 |
| **Phase 3** | ECS, Jobs, Persistence, UI (Parts IX–XII) | v3.0 |

## Goals

1. A reader can absorb the worldgen pipeline cover-to-cover and afterward read the actual Oxium worldgen source without needing further reference material.
2. Every reusable technique (FBM, Voronoi, SDF, D8 flow, splines, trilerp, MST, Poisson-disk, hashing) is taught in a primer chapter, and is linked to from every place it's later used.
3. Every "what the engine looks like at this stage" image in the book is *generated by the actual engine* from a pinned seed, so images cannot drift from code without CI noticing.
4. Interactive widgets exist for the math/algorithms where dragging a slider beats looking at a still — at minimum: noise, FBM, Voronoi, domain warping, splines, SDFs, trilerp, plate exploration, D8 flow stepping, cell-evaluator slicing.
5. The book is published at a stable URL on GitHub Pages, rebuilt on every push to `main`.

## Non-goals

- **Phase 2/3 content in Phase 1.** Rendering, mesher, lighting, ECS, jobs, persistence, UI are out-of-scope for Phase 1. The site sidebar shows them as "coming in v2.0 / v3.0" placeholders.
- **Localization.** English only.
- **Versioning of the book.** Docusaurus supports versioned docs; we don't use that for Phase 1. The book always describes `main`.
- **Comments / community features.** Pure read-only.
- **PDF / ebook export.** Web-only.
- **Playground widgets that compile arbitrary user code.** Widgets are fixed-purpose.
- **3D widgets in Phase 1.** Deferred to Phase 2 (renderer documentation).
- **Backwards-compatibility with any earlier doc tooling.** There is no prior doc site to migrate from.

## Site architecture

### Three navigation modes

The site supports three ways to find content:

1. **Linear (default).** Sidebar = Parts → Chapters → Sections, with "previous/next" buttons at the foot of every page. The intended cover-to-cover reading experience.
2. **By module.** Appendix A (Module Index) maps `src/worldgen/plates.rs → §3.1`, `src/worldgen/hydrology.rs → §3.4`, etc. For a reader who is in the code and wants the chapter that explains what they're looking at.
3. **By technique.** Appendix B (Technique Index) maps each reusable technique (FBM, Voronoi, SDF, D8 flow, …) to every chapter where it appears. For a reader who already knows the technique and wants to see every place the engine uses it.

### Voice and chapter shape

**Voice:** Rust-Book-flavored — second person, present tense, active voice, code-first, generous with worked examples. No "obviously," "trivially," "simply." No "TL;DR" summaries. No engagement framing ("let's dive in"). Every technique gets a one-clause definition the first time it appears in any chapter, even if Wikipedia has a longer one.

**Every chapter follows this skeleton:**

1. *Opening hook* — one paragraph: what we're trying to do, why it's hard, what we'll end up with.
2. *Intuition* — the picture, before any code.
3. *Build it* — code + math, in the order someone would write it.
4. *In the engine* — show the actual Oxium source (with `path:lineno` references), point out interesting deviations from the canonical version.
5. *What you can now do* — short callout listing the functions the reader can now read on their own.
6. *Next* — link to the chapter that builds on this one.

**Code blocks:**

- Always include a source comment on line 1: `// src/worldgen/plates.rs:42`. Reader can `grep` for the marker.
- Snippets are slightly simplified from the source where simplification aids reading — clearly marked `// simplified for exposition`. The "In the engine" section then shows the real code.
- Math rendered with KaTeX (via Docusaurus's `remark-math` plugin). Every equation pairs with a sentence defining each symbol.

**Cross-linking:**

- Every technique reference is a link to its primer chapter on first mention per chapter. (`We use [FBM](../part-1-foundations/1.4-fbm.md) at four octaves here.`)
- Every code reference uses `path:lineno`.

## Image strategy

Three image types, each used for what it does best.

### 1. Generated from the engine — "this is what Oxium actually produces"

A new binary `src/bin/doc_render/` reuses `worldgen_viz`'s rendering code and exposes a CLI:

```
doc_render --seed <BOOK_SEED> --center x,z --zoom <N> --stage <stage> --width <px> --output <path>
```

Where `<stage>` is one of the `probe::Stage` enum values plus a few new ones for chapter-specific renders (e.g. `DensitySliceY`).

Every "here's the heightmap field," "here's the flow accumulation," "here's the biome map," "here's a density slice" image in the book is produced by this binary at a pinned seed. They cannot drift from code without CI noticing (see below).

**Pinned book seed.** Phase 1 picks one seed — the **book seed** — that every generated image uses by default. Every chapter that shows the world near world-coords `(0, 0)` shows the *same* world. By chapter 4 the reader recognizes geography from chapter 2.

The book seed is declared in two places that must stay in sync:

- `docs/book/src/book.constants.ts` — used by widgets and MDX.
- `docs/book/tools/gen-images.sh` — the manifest of every image, with its `doc_render` flags.

### 2. Mermaid — "this is the system structure"

Inline `mermaid` blocks in MDX for: per-chunk fill dataflow, region cache state machine, density graph tree, dependency graph between modules, carve-precedence rule order. Renders to SVG. Easy to keep in sync with code (graph topologies change less often than numeric outputs).

### 3. Excalidraw / hand-drawn SVG — "let me explain a concept"

For math primers where labeled arrows beat code: how D8 picks a downhill neighbour, what trilerp's 8 corners are, how an ellipsoid SDF works, how `t = (d_b - d_a) / (d_b + d_a)` produces a smooth plate-boundary field. Excalidraw outputs SVG; the source `.excalidraw.json` is checked in alongside the rendered SVG so future-you can edit them.

### Image style rules

- Generated images: 4× resolution (Retina-ready), neutral background, fixed colormap per stage.
- Mermaid: default theme, no custom colors (Docusaurus dark/light toggle then Just Works).
- Excalidraw: thin sans-serif labels, two-color palette per diagram.

### CI parity check

A small CI job runs `tools/gen-images.sh` against the latest engine state and diffs the output against the checked-in PNGs. If anything changed, the PR gets a comment listing which images moved. Doesn't fail the build — the *purpose* of the check is to make the author aware, not to gate merges.

## Interactive widget strategy

Each widget is a single React+Canvas component embedded inline in an MDX chapter via JSX. The math under each widget is a TypeScript port of the corresponding Rust function, kept in `docs/book/src/math/`.

**Widget list for Phase 1:**

| Chapter | Widget | What it lets you do |
|---|---|---|
| 1.3 Coherent Noise | `NoiseField` | Toggle Perlin/Simplex, drag the seed, see the gradient grid overlay. |
| 1.4 FBM | `FbmExplorer` | Sliders for octaves, persistence, lacunarity. Live recompute. The headline widget. |
| 1.5 Voronoi | `VoronoiCells` | Drag seeds, watch cells re-tessellate. Toggle "show nearest" / "show 2nd-nearest" / "show boundary `t`". |
| 1.6 Domain Warping | `WarpToggle` | Same FBM, with/without warp, side by side; drag warp amplitude. |
| 1.7 Splines | `SplineEditor` | Drag control points of a cubic spline; show the climate→height analogy. |
| 1.8 SDFs | `SdfComposer` | Place ellipsoids and capsules; see the composed field; toggle `min`/`max` to see Boolean ops. |
| 1.9 Trilerp | `TrilerpDemo` | 8 corners with editable values; mouse over the interior to see the interpolated value; toggle "exact vs trilerp" error heatmap. |
| 3.1 Plates | `PlateExplorer` | Pan around a 2D plate map seeded from the book seed; click a column to inspect plate properties; toggle the ridge-lift overlay. |
| 3.4 Hydrology | `D8Stepper` | Step button advances flow accumulation one cell at a time, color-coded by accumulated area. |
| 4.2 Cell Evaluator | `CellGridSlice` | 2D slice of the 9×9 corner lattice; mouse over to compare exact vs trilerped values; visible error heatmap. |

**No hard cap on widgets** — additional widgets are welcome wherever dragging meaningfully beats looking. The guideline is: add a widget where it adds real understanding; don't add one just because you can.

### Implementation rules

- All widgets are pure-frontend (no backend). The math is a TS port of the Rust source — small enough functions (`fbm`, `voronoi_nearest`, `d8_dir`, `trilerp`) that this is reasonable.
- Each widget is a single `.tsx` file in `docs/book/src/widgets/`. Importable from MDX as `<FbmExplorer />`.
- A shared `useBookSeed()` hook so widgets default to the book seed when relevant.
- Lazy-loaded so the page renders fast even if a widget is 200 KB.
- Every widget has a static-image fallback for print / pre-hydration paint.

### TS-vs-Rust math parity

The widgets need TypeScript reimplementations of math functions that exist in Rust. To prevent drift:

- Each TS function in `docs/book/src/math/` has a comment pointing to its Rust source: `// parity: src/worldgen/plates.rs::voronoi_nearest`.
- A hidden parity-test page (not in sidebar) calls each TS function and renders a small "pass/fail" table comparing it to a baked-in Rust output set. We extend `doc_render` with a `--dump-parity` mode that prints reference outputs as a JSON file the parity page imports.
- Widget CI runs the parity page in headless mode and fails the build on regressions.

## Build, hosting, deployment

- **Build:** `cd docs/book && npm install && npm run build` produces a static site in `docs/book/build/`. Independent of `cargo build`.
- **Image generation:** `bash docs/book/tools/gen-images.sh` rebuilds every generated PNG using `cargo run --release --bin doc_render -- <flags>` for each image listed in the script.
- **Hosting:** GitHub Pages on the `gh-pages` branch. URL: `<user>.github.io/oxium/` by default; custom domain optional.
- **CI:** a GitHub Action on push to `main`:
  1. Runs `cargo build --release --bin doc_render`.
  2. Runs `tools/gen-images.sh` (regenerates all PNGs).
  3. Runs the widget parity test in headless mode.
  4. Runs `npm run build`.
  5. Deploys `docs/book/build/` to `gh-pages`.
- A separate **image-drift check** Action runs on PRs that touch `src/worldgen/`, `src/voxel/`, or `src/bin/worldgen_viz/`: regenerates the images and posts a PR comment listing any that changed. Doesn't fail the build.

## Phase 1 completion criteria

Phase 1 is "done" when:

1. All chapters in Parts I–V exist as committed `.mdx` files, each conforming to the chapter skeleton.
2. The 10 widgets listed above (plus any opportunistic additions) are implemented, lazy-loaded, with static-image fallbacks.
3. Every image referenced by the book is regenerable from `tools/gen-images.sh`.
4. The site builds cleanly with `npm run build`; no broken links; no missing image references.
5. Appendices A–D are populated.
6. The book seed is pinned in `docs/book/src/book.constants.ts`.
7. Deployed to GitHub Pages; URL works; the GitHub Action runs end-to-end on `main`.

## Risks

1. **Code drift.** As the engine evolves, line-number references and code excerpts go stale. The image-drift CI check catches *visual* drift. Line numbers themselves are fragile; we accept staleness and rely on `path:function-name` references that survive line motion. If staleness becomes painful, a follow-up could build a "snippet by symbol" tool.
2. **TS-vs-Rust math drift.** Mitigated by the parity-test page + widget CI (see Interactive Widget Strategy).
3. **Authoring time.** Rough order-of-magnitude estimate at sustainable part-time pace: foundations (Part I) ~3 weeks, overview (Part II) ~1 week, region build (Part III) ~4 weeks, chunk fill (Part IV) ~5 weeks, engineering (Part V) ~2 weeks, appendices + polish ~2 weeks. ~4 months total. Not a contractual estimate; sets expectations.
4. **`fluid.rs` scope unclear at design time.** The Fluid Settle chapter (4.8) may fold into Aquifers (4.7) after reading `fluid.rs` in detail during implementation. Acknowledged as a scoping decision deferred to writing.

## Open questions deferred to implementation

- **GitHub Pages URL / domain.** Defaults to `<user>.github.io/oxium/`. If a custom domain is preferred, add the CNAME during repo setup.
- **Book seed value.** Concrete value chosen during implementation after sampling a few candidates against `worldgen_viz` and picking one with visually-instructive geography (a continent, a long river, mountains, a clear archipelago, at least one Tropical biome).
- **Search.** Docusaurus's built-in Algolia integration is the obvious choice; can be deferred until content exists.
- **Whether to commit `node_modules/`.** Default: no. Lockfile is committed.
